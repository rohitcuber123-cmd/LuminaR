# Institution Part 2E: Analytics improvement review

Status: review only. All 20 requested ideas were assessed; none of the proposed capabilities below was implemented by this review. Priorities indicate dependency/risk order, not approval or a scheduled commitment. Current read-only analytics, UTC ranges, exact minor-unit semantics and explicit membership authority remain the completed phase scope.

P1 means an enabling correctness/privacy decision should precede dependent work. P2 means a useful bounded improvement after measurement or explicit product approval. P3 means later expansion requiring a separate domain/operational design.

| Requested item | Priority | Concrete improvement and prerequisite | Privacy / authority / correctness decision | This phase |
| --- | --- | --- | --- | --- |
| 1. CSV analytics export | P2 | Export the same authorized bounded aggregate definitions with library UUID, range, UTC boundaries, currency/minor-unit scale and generation time. Review maximum rows and spreadsheet formula escaping before implementation. | Fresh membership at download; ADMIN-only columns remain restricted. Never export member reading profiles or notification bodies. | REVIEWED; NOT IMPLEMENTED |
| 2. PDF report generation | P2 | Produce a dated printable aggregate report using the canonical API definitions and text/table equivalents. Verify wrapping and pagination for long subjects/titles and exact monetary strings. | Recheck authorization before generation/download; label unavailable sources and bounded trend windows explicitly. | REVIEWED; NOT IMPLEMENTED |
| 3. Scheduled analytics reports | P3 | Design explicit opt-in report schedules, recipient authorization, idempotency, retry/expiry and delivery retention after timezone policy is defined. | Revalidate membership/lifecycle at generation and delivery; revoked staff must not receive retained private reports. No automatic subscription. | REVIEWED; NOT IMPLEMENTED |
| 4. Library timezone setting | P1 | Specify a canonical IANA timezone field, ADMIN configuration and deterministic DST/date-boundary rules before local-date reports or schedules. | Historical UTC instants remain unchanged. Changing timezone must not silently reinterpret stored operations or cross tenant configuration. | REVIEWED; NOT IMPLEMENTED |
| 5. Custom date ranges | P2 | Add validated UTC/local-policy start-inclusive and end-exclusive intervals with maximum span, bounded buckets and query cost limits. | No unbounded client-supplied predicates; exact library authority applies to every interval. | REVIEWED; NOT IMPLEMENTED |
| 6. Acquisition spend analytics | P3 | First define authoritative acquisition cost, currency, adjustments and provenance. Sum verified purchase records only; current acquisition counts have no price source. | Never infer purchase spend from patron fees, book popularity or global metadata. Sensitive financial aggregates require an explicit role decision. | REVIEWED; NOT IMPLEMENTED |
| 7. Branch/campus analytics | P3 | Define canonical branch identity and book/holding/operation attribution, plus transfers and historical attribution rules. | A postal address or shelf string does not establish a branch. Library UUID remains the outer boundary; branch scope cannot widen membership. | REVIEWED; NOT IMPLEMENTED |
| 8. Shelf utilization | P3 | Define shelf capacity and dated location/holding changes before measuring utilization. Begin with explicitly labeled current stock placement if approved. | Existing shelf labels do not establish capacity or historical occupancy. Do not fabricate utilization percentages. | REVIEWED; NOT IMPLEMENTED |
| 9. Copy-level utilization | P2 | Measure loan/availability intervals only for verified COPY-mode identities with adequate persisted transition history; report coverage and exclude ambiguous aggregate-mode units. | Do not turn an anonymous aggregate holding into invented copy histories or member profiles. | REVIEWED; NOT IMPLEMENTED |
| 10. Cohort/retention analytics | P3 | Define aggregate membership cohorts and retained membership transitions, consent/purpose, retention and small-group rules before any cohort metric. | Exclude reading interests, named activity and top borrowers. Aggregate operational use alone does not authorize surveillance. | REVIEWED; NOT IMPLEMENTED |
| 11. Privacy thresholds for very small groups | P1 | Review which sensitive aggregate cells need suppression/minimum cohort sizes and protect against subtraction across filters/ranges. Distinguish unknown, suppressed and genuine zero. | Keep operationally necessary stock/queue totals usable. Any suppressed sensitive value must remain unavailable rather than fabricated zero. | REVIEWED; NOT IMPLEMENTED |
| 12. Analytics snapshots/materialization | P2 | Consider persisted aggregate snapshots only after larger-tenant benchmarks show a need; define library UUID, metric/version, UTC interval, source generation and recovery provenance. | A snapshot is derived evidence, never a new domain authority. Fresh membership applies even when data was generated earlier. | REVIEWED; NOT IMPLEMENTED |
| 13. Background precomputation | P2 | If materialization is justified, compute bounded tenant batches after canonical committed writes with retries, deduplication and rebuild/recovery isolation. | Analytics workers must not mutate inventory, loans, fees, reservations or events. Suspended/removed libraries require an explicit processing policy. | REVIEWED; NOT IMPLEMENTED |
| 14. Analytics cache invalidation | P1 | Define invalidation from audit/event/config generations before adding any cache. Keys need library UUID, range/bounds, metric version, filters and authorized capability shape. | Every cache hit revalidates current identity, membership and lifecycle. Revocation cannot be delayed by a cached ADMIN response. Current implementation has no cache. | REVIEWED; NOT IMPLEMENTED |
| 15. Platform fleet analytics | P3 | Propose safe installation/account/library lifecycle aggregates from the existing Platform authority model; review metric-by-metric privacy rather than summing everything available. | Platform assignment alone must not reveal private tenant lending, fees, reading activity or documents. Existing safe directory metadata is not a blanket exception. | REVIEWED; NOT IMPLEMENTED |
| 16. Anomaly detection | P3 | Evaluate deterministic aggregate integrity/operational thresholds with explicit baselines and false-positive review, after sufficient canonical history exists. | No individual borrower ranking or automated penalties. An alert is diagnostic and cannot repair domain data without a separately authorized operation. | REVIEWED; NOT IMPLEMENTED |
| 17. Admin-defined dashboards | P3 | Offer a curated whitelist of existing aggregate definitions and bounded display layouts only after metric versioning and privilege rules are stable. | No arbitrary Mongo pipelines, hidden joins, member drill-down or authority expansion through dashboard configuration. | REVIEWED; NOT IMPLEMENTED |
| 18. Chart library standardization | P2 | Select a shared chart system only if additional visualization benefits exceed dependency cost. Require readable six-viewport layouts, keyboard behavior, contrast and complete text/table equivalents. | Current subject bars and semantic trend tables remain valid; a chart must not invent absent history or hide unavailable sources. | REVIEWED; NOT IMPLEMENTED |
| 19. Long-term data warehouse | P3 | Design tenant-partitioned schemas, committed-event provenance, schema versions, retention, deletion propagation and reconciliation before any ingestion pipeline. | Pseudonymization alone is not authorization. Platform access and tenant business access remain distinct; no private RAG content ingestion. | REVIEWED; NOT IMPLEMENTED |
| 20. External BI export | P3 | Review explicitly approved export contracts, field minimization, destinations, credentials, audit, expiry and revocation after a bounded export model exists. | No external transfer, connector installation or credential creation occurred. Library authority must be checked before each release. | REVIEWED; NOT IMPLEMENTED |

Recommended order within future analytics work: privacy thresholds and cache invalidation design first; timezone policy before custom dates or schedules; measured bounded exports/charts next; materialization/precomputation only after demonstrated query cost. Acquisition spend, branches, warehouse and BI each require their own source/authority design.

The next major institution phase remains a separate digital-asset/private-document authorization audit. These analytics ideas do not start that phase or authorize exports, schedules, tracking, HNSW/KG builds or new tenant domains.
