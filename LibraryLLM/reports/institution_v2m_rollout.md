# Staged rollout — activation prohibited in Part2M

Stage1 is the isolated authenticated fixture: same canonical L runtime, one resident worker per child, real cached MiniLM/FAISS/KG, explicit opt-in, restricted writer and independently authenticated reader. Protected fixture secret files feed process environments in memory. Three builds per target and disabled/enabled/rotated/rollback phases produce native job/pointer evidence. Results are in rollout_validation.json; this is fixture evidence only.

Stage2 is a production-equivalent disposable environment, **not fully qualified here**. The151-book tenant workload matches the historical TEST scale but does not reproduce the full5M global Search deployment, actual service-account/DPAPI ownership, all tenants, peak concurrency, long-lived Mongo behavior or production authentication rollout. Auth-enabled fixtures are intentionally safer than the currently unauthenticated deployment. Matching source/model/build logic alone is insufficient for equivalence.

Stage3 requires runtime/default-disabled verification, restricted effective roles, namespace/validator/index ownership, secret DACL/DPAPI identity checks, current/previous observation consistency, native90s lease/10s renewal/2s idle/serial policy, startup/shutdown/resource measurements and native rollback. Review local medians/tails and limitations rather than deriving a production SLO from three small builds. Confirm operator diagnostics are local/read-only and Staff/Patron routes contain no infrastructure credentials or raw records.

Stage4 is an explicit operator approval gate. Required evidence includes assigned DBA/service/operator owners and SIDs, authenticated production application/Mongo boundary, protected secret enrollment and ACLs, single-resident service ownership, an agreed quiet window preventing new manual build submissions, source/data preservation, failure/rotation/revocation results, representative workload acceptance, monitoring/stop conditions and a rehearsed rollback. Current blockers mean this gate is not satisfied. No approval is inferred from a fixture PASS or the presence of credentials/collections.

Stage5 is future explicit activation, outside Part2M. No production user/role/collection/index/secret/ACL/flag is provisioned here; no production Search/Core/RAG/Recommendation/frontend process is launched, stopped or restarted. An approved existing owner must first establish native-safe quiescence using authoritative jobs/pointers and coordination with build-requesting Admins; a recent IDLE pulse is not a sufficient safety check. Do not invent a maintenance/cancel/drain API.

Future startup checks: operator independently verifies the intended single Search process/service registration, existing resident models, native database binding, explicit flag, exact writer privileges and the separate reader. Check namespace size/count/validator under DBA authority before enabling. Native writer startup must fail closed without schema creation or unrestricted fallback.

Monitoring remains evidence-based: inspect the fixed bounded worker supplement and unchanged J queue/jobs/artifact diagnostics using the reader principal; correlate library/job/target/fence/instance and publication acknowledgement. Recent pulse is a self-report, stale is an observation gap, progress time is a post-read observation, not exact commit or process verification. No HEALTHY/process-alive claim follows. Keep infrastructure evidence out of Staff UI.

Stop conditions: unexpected native state/pointer/fence changes, extra worker/model, unbounded writes/storage/threads/connections, wrong DB/principal, broad secret ACL, credential exposure, unexpected production enablement, excessive resource cost, malformed/future/uncorrelated evidence or inability to establish ownership/quiescence. Disable optional telemetry via the reviewed service procedure; retain native authority and evidence. No telemetry symptom triggers automatic retry/rebuild/recovery/cancel/unlock/delete/publication.
