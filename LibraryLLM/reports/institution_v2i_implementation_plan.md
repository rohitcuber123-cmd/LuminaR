# Part 2I reviewed implementation boundary

The frozen baseline was captured before production edits in `institution_v2i_baseline.json`, with exact source hashes and the four relevant original files under `.scratch/institution-v2i/before`. TEST currently has 151 eligible records, 150 holdings and 5 assets. Its latest indexed datasets contain 151 records. No count restoration is appropriate.

Source review found duplicate artifact verification inside a single Staff status request: `status → control_status → target_status → pointer_manifest`, followed by another target lookup and `pointer_manifest` in `control_status`. The isolated benchmark and a failing focused regression reproduce two verifications per target. A populated response makes 14 checksum opens. The 10,000-record baseline hashes approximately 93 MB. These are synthetic checksum-valid artifacts, not a qualified serving index.

The sole proposed production change is a private target-observation helper returning the existing status, the target row used for that status, and the verification outcome. `target_status` remains a wrapper returning precisely its established public dictionary. `control_status` consumes this observation directly. Each request still checks all referenced artifact bytes once per target, calculates the complete authoritative catalogue fingerprint, observes current durable jobs and checks current membership under the same tenant barrier. No cross-request observation, authorization, catalogue or artifact cache is introduced.

Acceptance: exact baseline/current response equality over READY, STALE, BUILDING, FAILED and RECOVERY_REQUIRED fixtures; corruption/missing/foreign artifacts detected on the very next request; fresh membership revocation and demotion enforced; mutations including direct repository writes and global enrichment remain visible; active and expired jobs retained; two-tenant isolation; actual worker/fault and frozen 2G/2H suites. Run identical paired benchmarks after implementation and report latency as measured, separately from the exact reduction in filesystem/database work.

Rejected for this phase: authoritative revision counters (no complete existing mutation protocol, including global enrichment), dirty markers, TTL status snapshots, cross-request verification caches, request coalescing, UI polling changes and new durable diagnostic fields. They require guarantees or measurements absent from the accepted implementation. Existing 503 tenant-barrier behavior is measured and retained, not hidden as a successful read.

No scheduler, extra worker, admission controller, automatic recovery, cancellation, cleanup, incremental indexing, public fleet endpoint or global ranking change is within this implementation. Workload and policy reports are designs only. No commit will be created. Preexisting regression failures remain reported and will not be repaired by changing historical expected hashes.
