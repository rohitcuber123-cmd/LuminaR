# Operator-owned secret lifecycle — fixture verified, production prerequisites unfulfilled

The actual runtime names are LUMINAR_WORKER_TELEMETRY_ENABLED, LUMINAR_WORKER_TELEMETRY_MONGO_URI and LUMINAR_OPERATOR_MONGO_URI. They are separate from the application's MONGO_URI. Native install binds the writer to the native job database. A URI alone does not enable telemetry; only the exact flag value1 permits factory construction. No secret-management platform is added.

Read-only host evidence found anonymous access to the production tenant namespace and broad project .env permissions: Authenticated Users may Modify and Builtin Users may ReadAndExecute. The audit did not read/report secret values or change production ACLs. The current project .env is unsuitable as an approved protected telemetry secret store. No deployment DBA/service owner, separate Search/operator OS identity, protected secret location or service-account DPAPI profile has been verified. These block production qualification.

## Concrete future manual procedure — not executed on production

1. Assign named DBA, Search service owner and infrastructure diagnostic operator. Record each approved OS SID, database, service launch method and ownership. The current audit observed MongoDB only on the inspected source-default service ports, so do not invent a Search Windows service name or assume a running worker/service account. Obtain a separately reviewed application/Mongo authentication hardening plan before any telemetry provisioning; enabling Mongo authorization without valid existing application principals could break unrelated services.
2. After separate approval, DBA uses an interactive authenticated administrative session. Read an admin password from a prompt, never argv, source, .env or a report. Verify the exact database/validator/index ownership, create the reviewed collection-scoped role and replacement-safe DB-local writer principal, and separately create a built-in read principal for the approved database. See writer_permissions.md and operator_permissions.md. No role/user installer exists in runtime or diagnostic tooling. Fixture provision functions reject production database names.
3. Enroll the writer URI as a SecureString **under the intended Search service OS identity on the intended host**, with that identity's DPAPI profile available. PowerShell Export-Clixml on Windows protects a SecureString for the encrypting user/machine. A file encrypted by the current interactive operator is not automatically decryptable by a different service account; ACL permission alone does not change DPAPI identity. Enroll the read-only URI independently under the intended operator identity. Do not create a machine-wide shared plaintext credential or a shared writer/reader OS account as an assumed shortcut.
4. Choose separate approved secret directories outside the repository, frontend roots, artifact stores, logs and shared temp folders. Before writing a secret, set a protected DACL with inheritance removed and access only for the owning service/operator SID and SYSTEM; set the owner deliberately. Verify the resulting SDDL and access rules, including absence of broad Users/Authenticated Users/Everyone grants. Retain an approved administrative recovery procedure; administrators/SYSTEM can ultimately override access, so this is not protection from an all-powerful host administrator.
5. In a one-time approved identity-specific enrollment session, use `Read-Host -AsSecureString` to input the URI and `Export-Clixml -LiteralPath <approved-secret-file>` to save the encrypted SecureString. Do not echo/decode it to the console. Re-read via `Import-Clixml` under the same intended identity, confirm type SecureString and verify an actual DB-local authenticated connection/effective privilege set without printing the URI. The exact file paths and service SIDs must be approved deployment evidence, not guessed here.
6. A reviewed existing launcher may decrypt in memory, set only the appropriate child-process environment variable and launch the existing single Search service with the **deliberate** enabled flag. No password appears in process arguments. Remove plaintext variables/environment entries in its finally path. Do not create a second Search/worker/model for monitoring. Stage5 activation is outside Part2M. The operator CLI gets only its reader URI through its own protected execution context, then removes the variable. Never use app JWTs or a Platform role as this credential.
7. Rotation: DBA creates a new DB-local principal with the same exact role and no additional inherited privileges. Enroll a new encrypted file under the same approved identity, verify its DACL/authentication, arrange a native-safe quiet window and perform a separately approved replacement of the secret/worker process. Confirm a fresh worker epoch, valid native pointers and read-only diagnostics. Revoke/drop the old principal after replacement validation; test both a fresh authentication and any relevant established connections. Do not assume that changing a password instantly expires every existing authenticated session. Preserve bounded telemetry/native history and retained artifacts.
8. Revocation/incident response: revoke the compromised principal through the DBA's independent authority, disable the explicit opt-in at the next controlled service restart, preserve sanitized evidence and verify canonical native job/pointer state. No telemetry outage authorizes rebuilding, retrying, cancellation, unlocking, recovery or cleanup. If a build is uncertain, use existing manually authorized native reconciliation/recovery semantics after lease/fence review. Do not let the reader credential mutate anything.
9. Rollback after credential failure: keep telemetry off, retain the existing native service credentials/protocol, and restart only through the approved ownership/runbook at a safe boundary. Do not delete secret files, accounts, generations, locks or job history automatically. Credential incident handling and production authentication/ACL changes remain separate explicitly approved work.

## Executed fixture evidence

Owned2M temp secret files used the current Windows identity and SYSTEM-only protected DACLs. Export-Clixml/Import-Clixml recovered the identical in-memory URI; UTF8/UTF16 plaintext was absent from file bytes. Native and operator child processes consumed the encrypted file without a password/URI in argv. Writer replacement/drop-old and reader replacement/drop-old were authenticated server-enforced tests. Ciphertext files, disposable accounts and owned Mongo data are removed with the fixture, not archived in repository reports.

Only the current Windows identity was exercised. Cross-account access/decryption, actual production service profiles, approved ownership, reboot behavior, service recovery and production ACL protection are **not qualified**. No production credential, encrypted secret file, OS user, ACL or service configuration was created or changed.

The Windows user/machine binding described above is also documented by [Microsoft Export-Clixml](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/export-clixml?view=powershell-7.4). This does not replace the local ACL and identity tests or qualify a different service account.
