The pure V5 prototype is `scratch/search_proof_recovery_v5/recompilation.py`. `completion.complete_draft` delegates to it. It is not wired into the production API, session store or frontend.

`issue_completion` derives a unique supported missing operand from server-owned IR. Its SourceEdit identifies the field, requirement IDs, exact original span/substrings, proposed replacement, original query digest, IR/controls digests, parser version, accepted plan version and expected resulting query. It accepts a value, not client-supplied authoritative offsets. Multiple unresolved same-field owners reject. Quote/newline injection, invalid numbers/orders and overlong results reject. Completion replaces an explicit marker; only a genuinely omitted terminal operand permits insertion at the owned boundary.

`issue_correction` supports apply and keep by changing source and reparsing it. Apply replaces the source-backed canonical repair operand. Keep is an explicit withdrawal of only the corrected positive category requirement, retaining the original operand as semantic content. Negative correction changes require explicit editing rather than broadening to semantic search. `issue_remove` implements explicit source-owned field removal. Other native transformations, including conversational refinements, bound/format/subject conflict choices and inherited context composition, are not fully integrated or qualified by this prototype.

`recompile` requires externally asserted fresh backend authorization and exact issued/current BoundContext equality: owner, login session, library, workspace, SMART mode, original query digest, parser version, accepted plan version, expiry and unused state. It reparses the original query under current authorized vocabulary, rejects changed IR/controls/projection, verifies exact original source replacement and expected resulting query, reparses the entire resulting query, validates capabilities/proof and compares untouched mandatory requirement fingerprints and hard projections. It returns a draft plus explicit original/result provenance. No commit is performed.

BoundContext and SourceEdit must remain backend-owned. Equality checks are not authentication, cryptographic issuance or durable single use. The caller's `authorized=True` is a test seam, not production authorization. Preview does not consume a choice. Real use needs the existing native fresh authority, one-use reservation, accepted-context version CAS and atomic revalidation of owner/version/expiry at commit. No CAS durability or crash recovery was tested here.

Native recovery confirmed these current definitions: `search/query_plan.parse_query` and `search/session_store.resolve` accept 500 characters; `search/interaction_api.ChoiceRequest.query` accepts only 150; `query_interaction.load_choice` requires exact stored raw-query equality. `query_interaction.transformer` completes by appending a value and mutates scalar fields for many operations. `offer`, `load_choice`, `reservation`, `ChoiceCommit`, `session_store.identity/resolve` and `interaction_api.authorized` remain unchanged. Their exact symbols/hashes are in the source map. The frontend `SearchAutocomplete.tsx` input also has maxLength 150; `SearchClarification.tsx` sends `clarification.original_query` unchanged.

The AST-only protocol audit tests current 150/151/500/501 behavior and an isolated 500-character schema proposal. Widening the raw query bound to 500 would resolve that transport mismatch, preserving exact equality. It is not sufficient for safe completion/recompilation or full search integration. A future authorized integration must align the API, initial query input, suggestions where appropriate, client types/validation, displayed accepted query, subsequent choice issuance, stored source provenance and session last-query semantics. It must distinguish submitted query from the fully recompiled accepted source and issue subsequent choices against that accepted source/digest. Never truncate to 150. A reference-only protocol is an alternative requiring its own lifecycle and binding design, not a silent workaround.

Focused tests exercise six completion fields, untouched conditions, correction apply/keep, removal, plan tampering, stale/foreign context, expiry, consumed state, injection and the 500-character boundary. There are 60 measured successful pure drafts across six fields, with no commit calls. The 30 additional SMART/EXACT cross-scope parser checks and eight schema checks are finite component diagnostics. Native correction_apply still works through the old transformer, but correction_keep still rejects with 422 because that transformer mutates fields without source recompilation. This safe rejection is a remaining integration incompatibility, not a successful user workflow.
